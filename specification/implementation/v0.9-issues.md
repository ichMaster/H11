# v0.9 — GitHub Issues

Issues for phase **v0.9 — Input as data** (version **v0 — Prototype 0: one deck, on the device, at
60 fps**), derived from the per-phase Tasks in [ROADMAP.md](../ROADMAP.md) (§v0.9) and the contracts
in [ARCHITECTURE.md](../ARCHITECTURE.md) (§Components, §Contracts, §Failure modes, §The device).
This file is scoped to a single phase; IDs continue from the previous phase
(H11-014 → **H11-015…H11-020**).

The phase turns the control scheme from source into data, and settles it before six versions each
append a key to the same dictionary. It creates one new seam — the action table — and one new
surface area the project has never touched: the PocketTerm's own buttons and its touch layer.

**Reconciled after H11-015 (2026-09-13).** The capture answered the phase's open question and raised
one the plan had not anticipated. **No button emits `BTN_*`** — all eight are ordinary keycodes
(`ARCHITECTURE.md` §Input has the table), so H11-016 needs no joypad path at all. But the buttons are
**the same physical codes the development keyboard scheme already uses**: `A` is `turn_left` and wants
to be `use`, `X` is `strafe_right` and wants to be `run`, `R` is `restart` and wants to be
`strafe_right`. The two schemes cannot both be live, so the owner chose **two profiles in the table**,
selected by `Game.on_device`. H11-016 and H11-018 below carry that; H11-017's conflict check applies
*within* a profile, never between them.

**Reconciliation note (Step 0.5).** `Game._setup_input()` builds the `InputMap` from `KEYMAP` using
`InputEventKey.physical_keycode` only: there is no joypad path and no touch path in the game today.
`ARCHITECTURE.md` mentions input once, in passing, inside the `Game` autoload bullet — there is no
§Input section, which is drift now that input becomes a seam. v0.8 landed two patterns this phase
reuses rather than reinvents: `Level._validate()` as the shape of release-safe validation of loaded
data (an `assert` is stripped and must never be the guard), and `tools/check_audio.py` as the shape
of adding a fourth acceptance gate.

## v0.9 — Input as data

### H11-015 — Capture what the PocketTerm's eight buttons actually emit

**Description:**
Before anything is bound, find out what X/A/B/Y/L/R/Select/Start physically send. The device's
keyboard advertises twelve `BTN_*` gamepad codes alongside its letter codes, and the system exposes
no joystick device — so those buttons may reach Godot as **joypad** input, which the current
`KEYMAP` (keycodes only) cannot see at all. Touches `specification/`.

**What needs to be done:**
- Capture raw events from the keyboard's `/dev/input/event*` node while each of the eight buttons is
  pressed in a known order. **This needs the owner at the device**; the capture itself is a short
  script that records and labels.
- Record the result in `ARCHITECTURE.md` as a table: button → event kind (`EV_KEY` with a `KEY_*`
  code, or `BTN_*`) → the code. This is the reference every later binding reads.
- Note in the same table which buttons are physically present, in case the eight are not all there.
- If they emit `BTN_*`, state explicitly that Godot will see them as joypad events and that
  `H11-016`'s table must bind both event kinds.

**Dependencies:** None

**Expected result:**
A table in `ARCHITECTURE.md` naming the exact event each of the eight buttons produces, so no later
issue has to guess.

**Acceptance criteria:**
- [ ] Every one of the eight buttons has a recorded event kind and code, or is recorded as absent
- [ ] The finding is written into `ARCHITECTURE.md`, not only into a chat message
- [ ] **Gate:** none — this issue produces a document, and the capture is its own evidence

### H11-016 — Input as a data table: data/input.json replaces KEYMAP

**Description:**
The seam. `KEYMAP` in `game.gd` becomes `data/input.json`, and `Game._setup_input()` builds the
`InputMap` from it. The table binds **keyboard, joypad and touch to the same action ids**, so nothing
downstream ever learns which device produced an action. Touches `scripts/`, `data/`,
`specification/`.

**What needs to be done:**
- `data/input.json`: **two profiles** (`desktop`, `device`), each an entry per action — `id`, `keys`
  (physical keycodes), a `display` name for the eventual rebinding UI, and `hold` (true for movement
  and run, false for taps like use and restart). No joypad field: H11-015 established that every
  button is a keycode.
- `Game._setup_input()` picks the profile from `Game.on_device` — the flag that already switches to
  fullscreen — reads it and applies it as `InputEventKey` events. `KEYMAP` is deleted, not left
  beside it.
- **Add a §Input section to `ARCHITECTURE.md`**: the table's shape, the rule that every device binds
  to the same action ids, the hold/tap distinction, and where the file lives. Input is a seam from
  this issue on, and `ARCHITECTURE.md` currently describes it in one passing clause.
- Ship the current twelve actions unchanged in the new file, so this issue is a pure move with no
  behaviour change: the keyboard scheme that works today must still work identically.

**Dependencies:** H11-015

**Expected result:**
Every binding in the game comes from `data/input.json`, and adding an action is a line in that file.

**Acceptance criteria:**
- [ ] `grep KEYMAP scripts/` returns nothing
- [ ] Playing on the Mac with the keyboard is behaviourally identical to before this issue (the
      `desktop` profile is the old `KEYMAP`, moved verbatim)
- [ ] **Contract test:** the action-table shape is pinned — a fixture table builds the expected
      `InputMap` actions and events, asserted in `--smoke`
- [ ] **Gate:** `--import` clean, `--smoke` green with the existing 18 checks unchanged
- [ ] Ties to the phase DoD: "every binding in the game comes from `data/input.json`"

### H11-017 — Validate the input table at load, including binding conflicts

**Description:**
A malformed or contradictory table must fail with a named reason, the way a malformed deck does
since v0.8 — and for the same reason: `assert` is stripped from release builds, so it can never be
the guard. Touches `scripts/`.

**What needs to be done:**
- Validate on load, following the shape of `Level._validate()`: unknown action ids, unknown key or
  button names, a missing required field, and an entry bound to nothing.
- **Binding conflicts:** the same key or button on two actions that can both receive it is a
  failure, not last-writer-wins. Report both action ids and the shared binding.
- Report like a bad deck: `push_error` with the first problem named, plus an on-screen message, and
  refuse to build a half-applied `InputMap`.

**Dependencies:** H11-016

**Expected result:**
A broken input table fails at load with a reason a person can act on, in a release build.

**Acceptance criteria:**
- [ ] Fixtures for an unknown action id, an unknown key name, a duplicate binding and an empty
      binding each fail with their own message
- [ ] The failure is visible in an exported build, not only in the editor
- [ ] **Gate:** `--smoke` gains an assertion per fixture; the real table stays green

### H11-018 — Bind the agreed device scheme to the eight buttons

**Description:**
Apply the scheme agreed in ROADMAP §v0.9: D-pad moves and turns, L/R strafe, B fires, A uses, X
runs, Y switches weapon (idle until v3.1), Start pauses/restarts, Select shows the fps counter until
v5.1 gives it the automap. Binds whichever event kind H11-015 found. Touches `data/`, `scripts/`.

**What needs to be done:**
- Fill the **`device` profile** in `data/input.json` with the eight buttons against the existing
  action ids, using the keycodes H11-015 recorded. The `desktop` profile is untouched, which is what
  makes the three colliding codes (`A`, `X`, `R`) a non-issue.
- **Verify what the D-pad emits.** H11-015 captured the eight face and shoulder buttons only; the
  scheme assumes the D-pad sends the arrow keycodes the `desktop` profile already binds. Confirm it
  with the same capture before relying on it.
- Add the two actions the scheme needs that do not exist yet: `pause` (Start) and `next_weapon` (Y).
  `next_weapon` is declared and does nothing until v3.1 — declared, not stubbed into `player.gd`.
- Keep the keyboard bindings intact beside them; they are the development scheme and must not
  regress.
- **This needs the owner at the device** to confirm the scheme is playable in the hand, not only
  that the events arrive.

**Dependencies:** H11-015, H11-016

**Expected result:**
The deck is clearable on the PocketTerm using only its own buttons.

**Acceptance criteria:**
- [ ] All eight buttons drive their agreed actions on the device, under the `device` profile
- [ ] The D-pad's actual codes are confirmed, not assumed
- [ ] The keyboard scheme is unchanged on the Mac
- [ ] A deck can be cleared end to end using the device's buttons alone
- [ ] **Gate:** `--smoke` on the Mac unchanged; a device pass confirming each button

### H11-019 — Touch as a second input device

**Description:**
The PocketTerm has a Goodix capacitive touchscreen the game has never used. Map screen zones to the
same action ids, so a touch is indistinguishable downstream from a key. Touches `scripts/`, `data/`.

**What needs to be done:**
- Zones for **fire** and **use** as the phase Tasks specify, declared in `data/input.json` beside the
  keys and buttons rather than hardcoded in a script.
- Feed them into the same actions via `Input.action_press`/`action_release`, so `player.gd` is
  untouched.
- Enable only when the platform reports a touchscreen; on the Mac the zones must not exist.
- Do not draw the zones: the HUD is a painted 640×480 layout and this phase does not redesign it.

**Dependencies:** H11-016

**Expected result:**
Fire and use work by touch on the device, and nothing changes on the Mac.

**Acceptance criteria:**
- [ ] Touching the fire zone fires; touching the use zone opens a door — on the device
- [ ] No touch handling is active when the platform reports no touchscreen
- [ ] **Gate:** `--smoke` green on the Mac (proving the zones are inert there); a device pass for the
      two zones

### H11-020 — Drive --smoke through action ids, and record the 67-key layout

**Description:**
The suite currently calls `player._fire()` and `player._use()` directly, so it never exercises the
input path at all — a broken table would pass every check. Drive it through actions instead, and
record the keyboard layout the scheme assumes. Touches `scripts/`, `specification/`.

**What needs to be done:**
- Replace the direct method calls in `_run_smoke()` with `Input.action_press`/`action_release` on the
  action ids, so the table is on the critical path of the suite.
- Confirm every bound key physically exists on the real 67-key PocketTerm keyboard and is reachable
  without an awkward modifier; **this needs the owner at the device**.
- Record that layout in `ARCHITECTURE.md` §Input so later versions bind into a documented scheme
  instead of guessing what the panel has.

**Dependencies:** H11-016, H11-018

**Expected result:**
The acceptance suite fails if the input table breaks, and the layout later versions bind into is
written down.

**Acceptance criteria:**
- [ ] `--smoke` drives fire and use through action ids and still passes 18/18
- [ ] Breaking a binding in `data/input.json` makes `--smoke` fail — negative-tested, not assumed
- [ ] The 67-key layout is recorded in `ARCHITECTURE.md` with every bound key confirmed present
- [ ] Ties to the phase DoD: "the button scheme is playable end to end on the device"

## v0.9 scope notes

**Total effort:** six issues — three M, three S; roughly a week.
**Critical path:** H11-015 → H11-016 → H11-018 → H11-020. The capture gates everything, because
binding the wrong event kind would be discovered only on the device.
**Phase DoD (roadmap §v0.9):** every binding comes from `data/input.json`; adding an action in a
later version is a line in that file and no GDScript change; a conflicting or unknown binding fails
at load with a named reason; the agreed button scheme is playable end to end on the device, whichever
event kind the buttons emit; and fire and use also work by touch.
**Contracts pinned this phase:** the action table shape (new seam — `ARCHITECTURE.md` §Input lands
with it in H11-016, and the contract test pins it); the rule that every input device binds to the
same action ids.
**Already discharged:** the phase's seventh task — "update v3.1's weapon switching to declare its
actions instead of appending to a dictionary" — was done when the scheme was agreed; ROADMAP §v3.1
already says *declared in `data/input.json`*. No issue is raised for it.
**Owner needed:** H11-015 (press eight buttons while events are captured), H11-018 (confirm the
scheme is playable in the hand) and H11-020 (confirm the 67-key layout). The pipeline will stop and
ask at each.
**Device note:** the budget is 16.67 ms measured on the PocketTerm with `--bench`, never estimated
on the Mac; **no paid APIs** anywhere in the acceptance path.
